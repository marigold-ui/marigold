Design tokens are the bridge between design decisions and code. They capture color, spacing, elevation, and motion as named variables so that every component speaks the same visual language. Names describe **purpose**, not appearance, so a token stays correct even when its value changes.

## How token names work

Tokens are used as Tailwind CSS utility classes. A class name has up to three parts:

```
border-destructive-accent
|       |          |
|       role       emphasis
property
```

- **Property**: the Tailwind prefix that determines the CSS property: `bg-`, `text-`, `border-`, `shadow-`
- **Role**: the semantic purpose: `primary`, `disabled`, `surface`, `hover`
- **Emphasis**: an optional intensity modifier: `-foreground`, `-accent`, `-surface`

For example, `border-destructive-accent` breaks down into the property `border-`, the role `destructive`, and the emphasis `-accent`, giving you the vivid red border used on error messages.

## Background and foreground pairing

Many tokens come in pairs: a background token and a `-foreground` token for text on that background. Always use the paired foreground when placing text on a colored background.

| Background            | Foreground                         | Example                            |
| --------------------- | ---------------------------------- | ---------------------------------- |
| `bg-primary`          | `text-primary-foreground`          | Buttons                            |
| `bg-selected-bold`    | `text-selected-bold-foreground`    | Binary controls (Checkbox, Switch) |
| `bg-destructive`      | `text-destructive-foreground`      | Error badges, section messages     |
| `bg-destructive-bold` | `text-destructive-bold-foreground` | Destructive button                 |
| `bg-access-master`    | `text-access-master-foreground`    | Master access rows                 |
| `bg-access-admin`     | `text-access-admin-foreground`     | Admin access rows                  |

**Tokens without a foreground pair:**

- `muted`, `hover`, `selected`, `focus-highlight`, `focus-highlight-bold`: the state washes. These are translucent and take whatever text color the ground already provides — but see [State fills and the alpha ramp](#state-fills-and-the-alpha-ramp), because "no foreground pair" does not mean "any text works". Body `text-foreground` is safe on all of them; `text-secondary` is not safe on `selected`
- `surface`: uses `text-foreground` or `text-secondary`
- `soft`: uses `text-foreground` (the near-white cap is light enough for regular text)
- `secondary`, `placeholder`: these ARE text tokens, not backgrounds
- `disabled`: primarily a text token. When a background is needed, pair with `bg-disabled-surface` (see [Disabled](#disabled) for details)

These tokens do not need a dedicated foreground color because `text-foreground` already clears contrast requirements on all of them. That guarantee covers `text-foreground` specifically — a dimmer text token on top of a wash has to be measured, not assumed (see [R8](#rules-for-alpha-tokens)).

    </DoDescription>
  </Do>
  <Dont>
    <DontDescription>

    </DontDescription>
  </Dont>
</GuidelineTiles>

<Callout title="foreground vs primary">
  `foreground` and `primary` share the same charcoal value but serve different
  roles. `foreground` is the default body text color. `primary` is the
  action/interaction color (buttons, selections). A theme could change `primary`
  to blue while `foreground` stays dark.
</Callout>

## State fills and the alpha ramp

Four tokens fill an element to signal a state rather than to mean something: `muted`, `focus-highlight`, `hover`, and `selected`. These are **washes**. They are translucent, and they are drawn from a dedicated alpha ramp rather than from the opaque charcoal steps, so that the same token reads correctly on a white card, on the gray page, and on a dark `ui-contrast` bar.

There are two ramps, because a wash has to darken a light ground and lighten a dark one:

| Rung    | Ramp A — dark base | Ramp B — light base | Fill vs. ground |
| ------- | ------------------ | ------------------- | --------------- |
| `a-50`  | 2%                 | 2%                  | 1.04:1          |
| `a-100` | 5%                 | 4.5%                | 1.11:1          |
| `a-200` | 11%                | 8.5%                | 1.27:1          |
| `a-300` | 19%                | 14%                 | 1.52:1          |

Ramp A is `charcoal-950` at those alphas and rides light grounds. Ramp B is `white` and rides dark grounds. The alphas differ between the two on purpose: a wash over a dark ground needs less alpha to read at the same strength, so each rung is solved to land on the same fill-vs-ground contrast within its own polarity. Equal _delta_ is the contract — the two ramps will never produce matching pixels, and they are not meant to.

The four jobs map onto the rungs one each: `muted` → `a-50`, `focus-highlight` → `a-100`, `hover` → `a-200`, `selected` → `a-300`. `focus-highlight-bold` reuses `a-300`. There are four rungs because there are four jobs; add a rung when a fifth job turns up, not before.

### Measured on both grounds and both scales

Every rung on every ground, with the wash measured against what it sits on and each ink measured on the composited wash. Both contrast models are reported, for the same reason the [charcoal matrix](#contrast-matrix) reports both: **WCAG 2.x** is the conformance target that 1.4.3 and 1.4.11 are written against, and **APCA** is the perceptual model from the WCAG 3 effort. They disagree most on light-on-dark pairs — exactly what ramp B creates — so the disagreements are where to look.

<ComponentDemo file="./alpha-ramp.demo.tsx" mode="preview" />

Two things are worth reading off that table. The wash column is a _band_, not a score to maximise: a wash is meant to be visible without reading as an indicator, so higher is not better. And on the contrast ground the whole ramp falls under APCA's low clip — APCA declines to call it contrast at all. That is not a defect in the ramp; it is R7 stated in stronger terms than WCAG can manage.

<Callout title="On a dark ground the tokens are restated, not repointed">
  `ui-contrast` restates all five wash tokens against ramp B, and descendants
  inherit them — so a hover, selection, or focus tint anywhere beneath a
  contrast surface flips with no component-level change. It has to restate each
  one individually. The tempting shorter version — a shared `--color-fill-*`
  seam repointed once — does not work, because a `var()` inside a
  custom-property declaration is substituted where that *declaration* applies,
  not where the token is used. `--color-muted: var(--color-fill-50)` written at
  the root resolves against the root's ramp, and descendants inherit the
  already-resolved color. That seam was in the first draft and measured 1.01:1
  on a dark ground, i.e. invisible.
</Callout>

Alongside the five washes, `ui-contrast` applies `text-primary-foreground` and restates the two text tokens that sit on the ground: `secondary` to `charcoal-400` (7.51:1) and `disabled` to `charcoal-600` (3.14:1). It deliberately does **not** restate `foreground` — components pinning `text-foreground` for emphasis should reach for `text-inherit` instead.

<Callout title="Why those two moved together">
  `secondary` was first restated to `charcoal-500` by lightness offset, mirroring
  how the token sits relative to `foreground` on light grounds. That clears AA at
  4.75:1, but it measures **Lc 36** on APCA against the **Lc 78** plain
  `secondary` reaches on white — and it left an inversion, because `disabled`
  measured 7.51:1 here, so a *disabled* label read louder than a merely secondary
  one. Exactly backwards from the light ground.

`disabled` turned out to be the mis-mirrored one: `charcoal-400` is a
deliberately quiet 2.31:1 on white and a shouting 7.51:1 here. Moving it to
`charcoal-600` restores that quiet at 3.14:1 — and frees `charcoal-400` for
`secondary`, which had been ruled out only because the two rungs collided
exactly. The result is Lc 55 for secondary, 2.21:1 from the primary text
(3.14:1 on light) and 2.39:1 from disabled.

</Callout>

The washes were not the only ground-dependent tokens — only the ones the ramp forced a decision on. To find the rest, the theme carries a **polarity inventory**: every neutral token is classified as either flipping under `ui-contrast` or deliberately stable, and a test asserts each behaves as classified. Adding a neutral token without classifying it fails that test, which is the point — "add a token, forget a line" is how the gaps appeared in the first place.

Working through it turned up three real failures, all now restated: `selected-bold` at 1.00:1 (charcoal-900 on a charcoal-900 ground, so a checked Checkbox or an ON Switch was invisible), `scrollbar-hover` at 1.14:1 (live — ActionBar's toolbar scrolls, so hovering its thumb made it disappear into the bar), and the inset focus ring at 2.05:1 over `selected`.

### What may flip, and what must not

The rest of the inventory is stable for one of two structural reasons, and they are worth stating because they decide the question for any future token.

**A token painted on an element's own opaque fill must not flip.** `ui-contrast` does not restate `surface`, so a field nested in a contrast region is still a white well. `placeholder` sits in that well at 5.52:1 and would be destroyed by a flip; so would `control-border` and its `-on-control` sibling, which trace the edge of a light control against a light track. This is the same reason `foreground` is deliberately not restated. `secondary-bold` is the sharpest case: it has two consumers, both on opaque light — Sidebar nav labels and the SegmentedControl label on its `charcoal-300` track — and no palette rung satisfies both polarities, 8.48:1 on white against 2.04:1 on the bar. It is a light-context ink by construction; use `secondary`, which does flip, for text that sits on the ground.

The corollary is that a token which _does_ flip has to be flipped **back** wherever a descendant paints its own opaque light fill — a Panel or a SelectList nested inside a contrast region is a white surface, and the dark-ground values are as wrong there as the light-ground ones were on the bar. The washes are the sharpest case: ramp B is a _light_-base alpha, so a hover or selection inside a nested white surface would tint white with white and vanish. `ui-polarity-reset` is the inverse of `ui-contrast` and does exactly that; `ui-frame`, `ui-soft` and `ui-state-disabled` all apply it, because each paints such a fill. The theme was already doing a one-property version — `ui-soft` applied `text-foreground` by hand to undo `text-primary-foreground`.

<Callout title="The two lists are kept in step by a test, not by discipline">
  `ui-contrast` restates a token and `ui-polarity-reset` restates it back, which
  means the same list is written twice. A test asserts that every token
  classified as flipping resolves, inside a `ui-frame` nested in a contrast
  region, to exactly its root value — so adding a restatement without adding the
  reset fails, and so does the reverse.
</Callout>

**A token painted at or outside an element's edge cannot flip either**, because `ui-contrast` is used two ways: as a **region** (ActionBar), where descendants really do sit on the dark ground, and as a **cap on a single control** (the primary and destructive Button), where the fill is dark but the focus halo and the boundary are painted against the light page. A restatement inherits and cannot tell those apart. That is why `ring` stays `charcoal-600`: the mid-tone is the point, clearing 3:1 on both polarities at a boundary (4.99:1 against the page, 3.14:1 against a dark cap). Flipping it to `charcoal-200` would take the Button's halo to 1.07:1.

Inset paint has no such ambiguity — it lands strictly inside the region — so the ring is split in two. `ring` covers the outset halo and the border recolor; `ring-inset` is what `ui-state-focus-item` draws, and it flips to `charcoal-200` (8.92:1 over a washed dark ground). The split is not cosmetic: no single value clears 3:1 on every backdrop of both polarities, because an inset ring has to survive both the `a-300` wash on the page and the `b-300` wash on the bar. The best any rung manages is 2.16:1.

<Callout title="The criterion is what a token is painted on">
  Not which ground its component happens to sit over. Every entry that once read
  as an unfixed gap turned out to be one of two things: a genuine failure, or a
  token measured against a ground it is never painted on. Getting that
  distinction right is what let the list close rather than grow.
</Callout>

### Rules for alpha tokens

These nine rules govern when a token may be translucent and how to use one. They are numbered because the theme source and the alpha test suite cite them by number.

**R1 — Alpha for the hierarchy layer; opaque for the meaning layer.** Alpha is for state fills, decorative rims, control edges, shadows, overlays, and scrims. Opaque is for text, the focus ring, status and access colors, structural lines that cross, and solid selection markers.

**R2 — Every alpha token carries a polarity.** Dark-base adapts across light grounds; light-base across dark grounds. Neither crosses over. A token is only "ground-adaptive" inside its own polarity, so say which one it belongs to.

**R3 — Derive polarity from the ink, not the surface.** Where an element has its own text color, prefer `bg-current/α`: `currentColor` already flips with the ground, so the element needs to know nothing about where it sits. Where it does not, the ground's own utility restates the wash tokens and everything beneath inherits the flip.

**R4 — One alpha per element; never stack.** Two translucent layers composite multiplicatively — 10% over 10% is an effective 19%, which turns a hover into something with the weight of a selection. Co-occurring states resolve to a single combined token. Watch overlapping siblings, not just nesting.

Stacking needs two _elements_. Two washes on the same element both set `background-color`, so the cascade picks one and nothing composites — and the winner must be the persistent state, never the momentary one. `selected` beats `hover` and `focus-highlight` today, and a test asserts it, because which one wins is decided by Tailwind's variant emission order rather than by anything this theme states.

That means the losing state becomes invisible, and at the top rung a combined token does not rescue it. Within R5 there is almost nothing left to spend: `selected` is 19% against a 20% ceiling, which buys 0.038 of contrast. But R5 is a convention (see below), so the load-bearing reason is not the budget — it is that a hovered selection _should not_ grow. Hover is momentary and selection is not, so a wash that strengthens under the pointer makes the transient state the loudest thing on the row. The ghost pair went the other way (`ui-state-selected-hover-ghost`, 10% → 15%) because there the selection layer is the only layer, so it has to carry both. Where the swallowed state is a focus indicator, the answer is a ring, not a wash.

**R5 — Budget: ≤ 20% on light grounds, ≤ 15% on dark.** A convention, not a measured cliff. Nothing changes at the ceiling: the cross-ground spread that matters — one alpha serving both light grounds — grows smoothly from 1.0% of the delta at 2% alpha to 1.4% at 19%, 1.5% at 20% and 1.8% at 30%. What the band buys is margin. Solving a wash for the 3:1 of a real indicator needs α ≈ 44% on light grounds and ≈ 33% on dark, so the budget holds every rung at roughly half the alpha at which a wash would stop being a wash. Read it as the line past which you should be reaching for an opaque token, not as a point where the math breaks.

**R6 — Never CSS `opacity` for a state.** Color-level alpha only. `opacity` fades text and icons along with the fill and silently destroys contrast; it is the most common way alpha tokens fail an audit.

**R7 — A state fill is reinforcement, never the only signal.** The ramp sits deliberately under the 3:1 non-text threshold — the top rung reaches 1.52:1. APCA says it more bluntly: the strongest rung anywhere measures Lc 25, under the Lc 30 that APCA asks of a control or focus indicator, and on the contrast ground the entire ramp falls below its low clip. Since APCA treats Lc 15 as the point below which many users will not see an element at all, a wash is not merely insufficient on its own — for some users it is not there. Anything signalling selection also carries an icon, a weight change, or an ARIA state.

**R8 — Text never goes alpha, and text _on_ a wash gets re-measured.** A wash changes what its own text sits on. `text-secondary` on `bg-selected` measures 3.60 / 3.27 / 3.10:1 on the surface, page, and contrast grounds — it fails WCAG 1.4.3 on all three, and APCA agrees at Lc 51 / 45 / 30. Selected rows take `text-foreground` (11.31:1, Lc 77).

Where a dimmer label is genuinely wanted, `text-secondary-bold` clears WCAG on light grounds — but only just, and not on both scales: on the page ground at `a-300` it is 5.02:1, which passes AA, against Lc 57, which misses APCA's Lc 60 floor for body text. Prefer `text-foreground` on the top rung and keep `secondary-bold` for `a-50` and `a-100`.

**R9 — Tune α to a contrast target, not to a matching hex.** Solve each rung for the ratio it must hit on its own grounds, and accept that the two polarities produce different colors. Check the solve on both scales: a target met in WCAG 2.x alone can still be perceptually thin on a dark ground, which is exactly how the `secondary` restatement above ended up at Lc 36.

<GuidelineTiles>
  <Do>
    <DoDescription>
      Use `bg-current/α` for elements that float over grounds the theme can't
      predict, and the wash tokens for elements whose ground it knows.
    </DoDescription>
  </Do>
  <Dont>
    <DontDescription>
      Don't stack two washes on one element, and don't reach for CSS `opacity`
      to express a state — it drags text contrast down with the fill.
    </DontDescription>
  </Dont>
</GuidelineTiles>

### Control

Controls carry two neutral tokens. Most define their shape with a border, drawn with `control-border` through the `ui-control` utility. A few communicate their state through a filled background instead, and that resting fill is the `control` token.

`control-border` is the visible edge of a bordered control such as a text input or a select. It is the denser sibling of `surface-border`, kept above the contrast threshold so the boundary is always seen. The full set of edge tokens lives under [Borders](#borders).

Some controls have no border to define them. The switch track is the clearest example. When OFF, the track needs to look like a solid, physical groove that the thumb can slide along. A white or transparent background would make it disappear into the surface, while `selected` or `disabled-surface` would send the wrong signal. `control` fills this gap with a medium-weight neutral background that reads as an interactive control in its resting state, and it pairs naturally with `selected-bold` for the ON state.

### Selected

Selection tells users which item has already been chosen. Not every selection looks the same though. Binary controls like checkboxes and switches flip between on and off, so they use `bg-selected-bold` with `text-selected-bold-foreground` for a strong, inverted style that clearly communicates the on/off state. List-based components use the quieter `bg-selected` wash paired with the row's own indicator (the checkbox, radio, or check icon), which carries the selection boundary and its WCAG 1.4.11 contrast. The wash sits one step darker than the `hover` fill, so a committed row reads heavier than one the cursor merely floats over.

<Callout title="Known issue: secondary text on the selected wash">
  Secondary description text (`text-secondary`) on a selected row lands at
  3.60:1, below the 4.5:1 AA minimum — and moving the fill onto the alpha ramp
  did not change that, because the rung was solved to match the opaque value it
  replaced. Selection is carried by the indicator, so the failure is limited to
  the description subtext. Render selected-row descriptions in `text-foreground`
  (11.31:1) instead. See [R8](#rules-for-alpha-tokens) for the full picture,
  including why `text-secondary-bold` is not a safe substitute on this rung.
</Callout>

### Focus highlight

Focus highlight accompanies the item the user is currently navigating to via keyboard. Unlike selection, which shows a confirmed choice, focus indicates where the user's cursor is right now. Two intensities handle different contexts: a subtle tint for menu items and drop zones, and a bolder fill for inline segments like date fields where the focused part needs to stand out clearly.

<Callout title="A focus tint, not a focus indicator">
  Despite the name, neither token can serve as the focus indicator. Both are
  washes, and every wash sits deliberately below the 3:1 threshold [WCAG
  1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)
  asks of a non-text indicator: `focus-highlight` measures 1.11:1 on a white
  surface and `focus-highlight-bold` reaches 1.52:1. Solving a wash for 3:1
  would need roughly 44% alpha — over twice the budget, and darker than
  `selected`, so it would read as a selection rather than a focus. In a menu the
  tint is doubly unreliable, because focus follows the mouse there and the same
  wash fires on hover. The perceivable affordance is always a ring:
  `ui-state-focus` for framed controls, `ui-state-focus-item` for borderless
  rows, both drawn from `ring`. Let the tint track the cursor and the ring prove
  where keyboard focus actually is — use these tokens **with** a ring, never
  instead of one.
</Callout>

<TokenTable
  tokens={[
    {
      name: 'focus-highlight',
      value: 'charcoal-a-100 (charcoal-950 / 5%)',
      useFor:
        'Subtle focus tint accompanying a focus ring (Menu, FileField). Not a focus indicator on its own',
    },
    {
      name: 'focus-highlight-bold',
      value: 'charcoal-a-300 (charcoal-950 / 19%)',
      useFor: 'Stronger focus tint for inline segments (DateField)',
    },
  ]}
/>

```tsx
// Subtle tint plus the ring that carries the indicator: menu items, drop zones
<div className="focus-visible:bg-focus-highlight focus-visible:ui-state-focus-item" />

// Bold focus: inline segments like date fields
<div className="data-focused:bg-focus-highlight-bold" />
```

<GuidelineTiles>
  <Do>
    <DoDescription>
      Use `bg-focus-highlight` for list-like navigation (Menu, FileField) and
      `bg-focus-highlight-bold` for inline segments (DateField) where the
      focused part needs stronger contrast.
    </DoDescription>
  </Do>
  <Dont>
    <DontDescription>
      Don't let a focus highlight be the only focus indicator. On its own it
      lands at 1.11:1 — 1.05:1 where a caller halves it, as FileField does — and
      in a menu it also fires on hover. Add `ui-state-focus` or
      `ui-state-focus-item` alongside it.
    </DontDescription>
  </Dont>
  <Dont>
    <DontDescription>
      Don't use `bg-selected` for focus states. Selection and focus are
      different concepts: selection is a confirmed choice, focus is where the
      keyboard cursor currently sits.
    </DontDescription>
  </Dont>
</GuidelineTiles>

### Hover

Hover feedback tells users that an element is interactive. Unlike disabled or selected states, hover is momentary and must feel lightweight. Two patterns handle different contexts, and both are translucent — what differs is **where each one gets its polarity from** (see [State fills and the alpha ramp](#state-fills-and-the-alpha-ramp)).

<TokenTable
  tokens={[
    {
      name: 'hover',
      value: 'charcoal-a-200 (charcoal-950 / 11%)',
      useFor: 'Hover background for menu items, list options, sidebar links',
    },
  ]}
/>

<Callout title="Why two hover patterns?">
  `ui-state-hover` uses the `hover` token, which is fixed to one polarity per
  ground: dark-base on light grounds, flipped to light-base under `ui-contrast`.
  That is right for elements whose ground the theme knows — list items, table
  rows, menu items, sidebar links. `ui-state-hover-ghost` instead derives its
  polarity from the element's own ink (`bg-current/10`), which is what ghost
  buttons, tabs, and ActionBar buttons need: they sit on grounds the token layer
  cannot predict, and `currentColor` already flips with the ground.
</Callout>

```tsx
// Ground-derived hover: list items, table rows, menu items, sidebar links
<div className="hover:ui-state-hover" />

// Ink-derived hover: ghost buttons, tabs, action bar buttons
<div className="hover:ui-state-hover-ghost" />

// A selection layer that must also carry hover: one combined value, not two
<div className="ui-state-hover-ghost hover:ui-state-selected-hover-ghost" />
```

The `ui-state-hover` utility applies `bg-hover` with `text-foreground`. The `ui-state-hover-ghost` utility applies `bg-current/10`, a 10% translucent overlay of the current text color.

`ui-state-selected-hover-ghost` exists because hover and selection can be true at once, and R4 forbids stacking them. It applies `bg-current/15` as a single layer. Letting the two compose instead yields an effective 19%, which is above the dark-ground budget and reads with the weight of a selection rather than a hover.

<GuidelineTiles>
  <Do>
    <DoDescription>
      Use `ui-state-hover` for items whose ground the theme knows, like list
      items, table rows, menu items, and sidebar links.
    </DoDescription>
  </Do>
  <Dont>
    <DontDescription>
      Don't use `ui-state-hover` on ghost buttons or tabs. Use
      `ui-state-hover-ghost` instead so the hover derives its polarity from the
      element's own ink.
    </DontDescription>
  </Dont>
</GuidelineTiles>

### Disabled

Disabled elements must look visually inactive so users don't try to interact with them. Not every disabled element needs the same treatment though. A disabled label or help text only needs dimmed text, while a disabled input or button also needs a gray background to signal that the entire control is inactive. Two tokens handle these cases.

<TokenTable
  tokens={[
    {
      name: 'disabled',
      value: 'charcoal-400 (charcoal-600 on a contrast ground)',
      useFor:
        'Disabled text color. Deliberately quiet — 2.31:1 on white, and restated so it stays that quiet on a dark ground',
    },
    {
      name: 'disabled-surface',
      value: 'charcoal-100',
      useFor:
        'Disabled background for full controls (paired with text-disabled)',
    },
    {
      name: 'disabled-border',
      value: 'charcoal-300',
      useFor:
        'Boundary of a disabled control: a soft, receding edge (applied via ui-state-disabled, so the border dims rather than disappears)',
    },
  ]}
/>

Most token pairs follow the pattern `bg-X` + `text-X-foreground`. Disabled is different because `disabled` is primarily a **text** color, not a background. Many disabled elements only need dimmed text on a white surface (labels, menu items, help text). Only full controls like inputs and buttons need a gray background on top of that. So `disabled-surface` is the optional background add-on, while `disabled` itself is the text color. The pair is `bg-disabled-surface` + `text-disabled`, reversed from the usual direction.

```tsx
// Text-only disabled (labels, help text, menu items)
<span className="text-disabled cursor-not-allowed">Disabled label</span>

// Full disabled control (inputs, buttons)
<input className="bg-disabled-surface text-disabled cursor-not-allowed" />
```

The `ui-state-disabled` utility bundles background, text, and cursor into one class. Its edge is the `disabled-border` token, listed with the other boundaries under [Borders](#borders).

### Borders

Every boundary token in one place. Marigold draws element edges with five tokens, and each one answers a different question. There is the decorative rim of a surface, the visible edge of a control, that edge dimmed for a disabled control, the structural divider, and the focus ring. `surface-border` also appears in the [Surfaces](#surfaces) section, `control-border` in the [Control](#control) section, and `disabled-border` in the [Disabled](#disabled) section, and they are repeated here so the whole set is discoverable at a glance. See [Form Fields](/foundations/form-fields) for component-level guidelines and [Elevation](/foundations/elevation#surfaces-and-controls) for the surface and control rule these tokens implement.

<Callout title="Which border token to pick for the job">
  Each boundary answers a different question. `surface-border` is the
  **decorative** rim of a raised surface (Card, Panel, Dialog). It sits below
  the contrast threshold, so never use it where the edge has to be seen.
  `control-border` marks an element you **operate**. It is the same translucent
  charcoal stroke as `surface-border` at about twice the density, so it stays
  clearly visible and adapts to the ground beneath it. `disabled-border` is that
  control edge **dimmed** for an inactive control, receding rather than
  vanishing. `border` draws **structural lines** such as dividers, grid lines,
  and section rules. It is opaque on purpose, because separators are many
  strokes drawn by many cells and translucent strokes would render darker
  wherever they cross. `ring` is the **focus** outline, the perceivable
  affordance for keyboard users.
</Callout>

### Status colors

Status colors communicate feedback to the user: errors, confirmations, warnings, and informational messages. Components like Badge, SectionMessage, and Toast use these tokens to convey meaning through color.

Every status follows the same `bg-X` / `text-X-foreground` pairing as other tokens. On top of that, an accent level adds a higher-intensity variant for borders and icons. Here is how the pattern looks using `destructive` as an example:

| Token suffix       | Role                                          | Example usage                                                                       |
| ------------------ | --------------------------------------------- | ----------------------------------------------------------------------------------- |
| `destructive`      | Subtle background for containers              | `bg-destructive` on Badge, SectionMessage, Toast                                    |
| `-foreground`      | Text on that background                       | `text-destructive-foreground`                                                       |
| `-accent`          | Vibrant, saturated variant for borders, icons | `border-destructive-accent` for accent borders, icon colors in Toast/SectionMessage |
| `-bold`            | Strong fill background (destructive only)     | `bg-destructive-bold` for destructive button                                        |
| `-bold-foreground` | Text on a bold background (destructive only)  | `text-destructive-bold-foreground` on destructive button                            |

Replace `destructive` with `success`, `warning`, or `info` for the other statuses. Most statuses only need the first three levels. The `-bold` / `-bold-foreground` pair exists only for destructive, where a solid red button needs a dedicated fill and contrast text.

```tsx
// Subtle container: light background + dark text
<div className="bg-destructive text-destructive-foreground">Error</div>

// Accent border on a subtle container
<div className="bg-warning border-warning-accent text-warning-foreground" />

// Accent icon color
<svg className="text-destructive-accent" />

// Strong fill: bold background + bold-foreground text
<div className="bg-destructive-bold text-destructive-bold-foreground">
  Delete
</div>
```

</GuidelineTiles>

## Elevation

A single shadow marks the one layer that floats above the page. Everything else in normal flow separates by fill and boundary instead: cards and panels by the gray page ground, buttons by a raised cap (`ui-soft`, `ui-contrast`), fields by a flat well (`ui-control`).

| Token                      | Use for           | Components                                      |
| -------------------------- | ----------------- | ----------------------------------------------- |
| `shadow-elevation-overlay` | Floating elements | Dialog, Drawer, Menu, Popover, Toast, ActionBar |

Shadows are generated using the [Josh Comeau shadow palette technique](https://www.joshwcomeau.com/shadow-palette/) with multiple layers for natural-looking depth.

See [Elevation](/foundations/elevation) for visual examples and usage guidelines.

## Spacing

### Control heights

All interactive controls share a consistent height scale.

| Token             | Value          | Use for                               |
| ----------------- | -------------- | ------------------------------------- |
| `h-control`       | 2.25rem (36px) | Default height for buttons and inputs |
| `h-control-small` | 2rem (32px)    | Compact buttons and controls          |
| `h-control-large` | 2.5rem (40px)  | Large buttons                         |

### Relational spacing

Semantic spacing tokens for gaps between elements. The scale increases with the visual distance between items: tightly coupled elements sit close together, independent sections get more breathing room.

| Token     | Value | Use for                              |
| --------- | ----- | ------------------------------------ |
| `tight`   | 6px   | Closely related items (icon + label) |
| `related` | 8px   | Items in a group                     |
| `regular` | 24px  | Independent items                    |
| `group`   | 48px  | Groups of content                    |
| `section` | 96px  | Major page sections                  |

For visual examples and detailed guidance on when to use each level, see [Spacing](/foundations/spacing).

### Inset spacing

Padding tokens for inside elements, available in three aspect ratios:

- **Square**: equal padding on all sides
- **Squish**: more horizontal than vertical (buttons, action items)
- **Stretch**: more vertical than horizontal (cards, stacked content)

Each comes in five sizes: tight, snug, regular, relaxed, loose. For the full list of values and visual examples, see [Spacing](/foundations/spacing).
