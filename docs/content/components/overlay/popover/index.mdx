The `<Popover>` component opens a floating panel next to a trigger. The panel holds whatever you put in it: text, a list whose rows have their own controls, a few form fields, or a search over a list. People stay in the panel and work with its content, and it closes when they dismiss it.

Use `<Popover>` when the content is a small surface of its own, like a notifications panel, a set of filters or a profile card. When the panel is a list of commands that run and close, use a [`<Menu>`](/components/overlay/menu) instead.

## Usage

`<Popover.Trigger>` wraps the trigger, usually a [`<Button>`](/components/actions/button), and the `<Popover>` it opens. Inside the popover, start with a [`<Title>`](/components/content/title) and an optional [`<Description>`](/components/content/description). They form the panel's header, and the title becomes its accessible name. Put the body in `<Popover.Content>`. When the panel runs out of room, only the content scrolls and the header stays in place.

<ComponentDemo name="popover-basic" />

On small screens the panel opens as a tray from the bottom of the screen, with a close button. You write the content once and it works in both places.

`<Popover.Content>` is optional. Without it, the popover lays out all its children as the body and scrolls them together, title included. Use it whenever the panel has a title or can get long. When the body is a form, put the [`<Form>`](/components/form/form) inside `<Popover.Content>`, not around it, so the content can still scroll.

### Popover vs Menu

A menu is a choice. A popover is a place. In a menu every row is a command: the user picks one, it runs, and the menu closes. In a popover the user stays and works with whatever is inside.

Ask one question to decide: after the user does the main thing inside, should the panel close on its own? If yes, use a menu. If no, use a popover.

There is also a hard rule. If any row contains its own interactive control, such as a switch, a second button, a link or an input, it can't be a menu. Screen readers do not expose controls inside a menu item, and keyboard focus never reaches them.

| Question                                                     | Menu                                               | Popover                                                      |
| ------------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------------------ |
| Is every row a command?                                      | Yes                                                | —                                                            |
| Does it close after one selection?                           | Yes                                                | No, it stays open                                            |
| Can rows contain their own controls?                         | No                                                 | Yes                                                          |
| Can it hold any layout, like text, sections and form fields? | No                                                 | Yes                                                          |
| Keyboard                                                     | One tab stop, arrow keys between items, type-ahead | Tab moves through the controls inside                        |
| Selecting rows                                               | Built in with `selectionMode`                      | Put a [`<ListView>`](/components/collection/listview) inside |

Toggles are where this gets mixed up. When the row itself is the toggle, like showing or hiding table columns, use a menu with selection. When each row is content that happens to have a switch, like a notification you can mute, use a popover with a list inside, so the switch is reachable.

### Lists with controls

For rows that people operate, put a [`<ListView>`](/components/collection/listview) inside the popover. Each row can carry its own buttons and an action menu, and the list keeps arrow key navigation between rows. A notifications panel is the typical case. Put the list directly in `<Popover.Content>`. Its divider lines then reach the popover's edges while the row text stays aligned with the title. At the bottom of the panel, and right under a search, the list also drops the content's padding, because its rows bring their own. Content before or after the list keeps its spacing.

When the list sits inside another element, or for other edge-to-edge content like an [`<Accordion>`](/components/navigation/accordion), set `bleed` on `<Popover.Content>` to remove its horizontal padding.

### Searching a list

Put a `<Popover.Search>` above the `<Popover.Content>` holding a list to filter the list as the user types. Search belongs in a popover when people act on the rows in place, like changing a team member's role or removing them. To let people type and pick one value, use an [`<Autocomplete>`](/components/form/autocomplete) or a [`<ComboBox>`](/components/form/combobox) instead.

The search is a borderless row that spans the popover and stays in view while the results scroll. It takes focus when the panel opens, and Tab moves on into the results. Items are matched by their `textValue`. The field has no visible label, so give it an `aria-label` and a placeholder that both say what is searched.

<ComponentDemo name="popover-search" />

Under a `<Title>`, the search sits between two dividers. Leave the title out and the search becomes the popover's header, for a more compact panel. The popover then needs an `aria-label`.

### Filters and short forms

A popover can hold a few form fields, like a filter panel that applies on a button press. Put the closing buttons in the `close` slot with `slot="close"` and the panel closes when they are pressed.

<ComponentDemo name="popover-filter" />

Keep forms in a popover short and optional. A popover closes when the user clicks away, so ask whether dismissing it loses work or blocks the user. If it does, use a [`<Dialog>`](/components/overlay/dialog).

</GuidelineTiles>

### Modality

A popover is modal by default, following React Aria. While it is open, the rest of the page is hidden from assistive technology, scrolling is locked, and focus stays inside the panel. This is right for almost every popover.

Set `nonModal` to let focus leave the panel and keep the page interactive. React Aria warns against this when the panel holds buttons, links or fields, because screen reader users can lose track of where they are. Keep `nonModal` for panels without focusable controls. On small screens the panel opens as a tray, which is always modal.

### Placement and width

Use `placement` to position the panel relative to its trigger, for example `bottom end` for a panel opened from an icon in the top right corner. React Aria flips the panel when there is not enough room. Set `width` to `small`, `medium` or `large` to match the content. The default is `medium`.

### When not to use a popover

A popover can hold anything, which makes it easy to reach for. Most needs already have a more specific component.

| Need                                                                      | Use instead                                                                            |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| A list of commands that run and close                                     | [Menu](/components/overlay/menu)                                                       |
| Context or overflow actions behind a "⋮" button                           | [ActionMenu](/components/overlay/action-menu)                                          |
| Choosing one or more values for a form                                    | [Select](/components/form/select)                                                      |
| Typing to pick one value, with nothing else to do on the rows             | [Autocomplete](/components/form/autocomplete) or [ComboBox](/components/form/combobox) |
| Entering several tags                                                     | [TagField](/components/form/tag-field)                                                 |
| A short, passive hint on hover                                            | [Tooltip](/components/overlay/tooltip)                                                 |
| A "?" or "i" help button                                                  | [ContextualHelp](/components/overlay/contextual-help)                                  |
| Required input, several steps, a destructive confirmation or wide content | [Dialog](/components/overlay/dialog)                                                   |
| A system message without a trigger                                        | [Toast](/components/overlay/toast)                                                     |

### Things to avoid

- **Don't nest popovers.** Opening a popover from inside another one is hard to follow and hard to dismiss. Field dropdowns, like a Select inside a filter panel, are fine.
- **Don't put required or critical input in a popover.** If the content is wider than about four columns, it needs a Dialog.
- **Don't repeat what is already on the page.** A popover should add information, not copy it.
- **Don't open a popover from the primary action.** Popovers carry secondary and contextual content.

## Accessibility

The panel is a dialog. A `<Title>` inside `<Popover>` becomes its accessible name automatically. When the panel has no visible title, give `<Popover>` an `aria-label`. An icon-only trigger needs an `aria-label` too.

The trigger exposes whether the panel is open. When the panel opens, focus moves into it. Tab moves through the controls inside, and Escape closes the panel and returns focus to the trigger. Set `keyboardDismissable={false}` on `<Popover.Trigger>` only when there is another clear way out, because a panel the keyboard can't leave is a barrier.
