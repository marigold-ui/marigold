feat(DST-1625): track `search_docs` MCP tool usage in telemetry so Insights can report call volume, unique callers, error rate, and top-searched doc topics. The event schema is now a discriminated union over `cli_command` and `mcp_tool_call`, and the rate-limit/persist logic moves into `api/telemetry/record.ts` so the MCP route can record in-process instead of the server POSTing to itself. Callers are identified only by an HMAC-SHA256 digest of their Keycloak `sub` (`MCP_TELEMETRY_HASH_SECRET`), never the raw claim, and the public `POST /api/telemetry` endpoint accepts CLI events only.

Consumer-visible for anything reading the telemetry store: events no longer go into per-day `telemetry:YYYY-MM-DD` lists but into a single `telemetry:events` stream, appended with `XADD` and read with `XRANGE`. Stream ids are `<epochMillis>-<seq>`, so any time window is one command rather than one `LRANGE` per day, and each entry carries the JSON event in a field named `data`. `mcp_tool_call` entries are interleaved with `cli_command` ones, discriminated on `event`. The stream carries no TTL and is not trimmed, so history is kept indefinitely — a deliberate reversal of the 90-day TTL DST-1475 put on the old daily lists, and it applies to CLI telemetry too now that both sources share one stream. Rationale in `.memory/adr/0006-telemetry-retention.md`. Existing data in the old daily lists is not migrated and is no longer read by anything; it needs no cleanup either, since that 90-day TTL expires every remaining list within 90 days of this shipping. Rate-limit keys also gain a source prefix (`telemetry:rl:{id}:{date}` → `telemetry:rl:cli:{id}:{date}`), which resets in-flight CLI quotas once on deploy and orphans the old keys until their ≤24h TTL expires. Since nothing expires the stream any more, the quotas are what bound its growth: the per-caller ceiling is now per source (1000/day for CLI, 10 000/day for MCP, whose id comes from a verified JWT), and `POST /api/telemetry` gains a second quota keyed on the client address (`telemetry:rl:ip:{ip}:{date}`, 20 000/day) because the per-caller key on that endpoint comes out of the request body. Over-quota addresses get a 429; a quota check that cannot run lets the request through.
